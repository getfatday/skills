# document-upgrade

Bring a repository's materialized document-plugin artifacts current with the
installed plugin. **Read-mostly** — only acts on a file after the user sees a
plan, and on hand-edited files only after a per-file confirmation with diff.

The deterministic mechanics — discovery, provenance parsing, version
comparison, classification — live in
`${CLAUDE_PLUGIN_ROOT}/scripts/upgrade-scan.py`. This skill consumes its
JSON output and runs the judgment loop. Layer-1 tests cover the script;
this skill's behavior is covered by `evals/evals.json`.

## When to run

- The user installed a newer `document` plugin and wants this repo
  refreshed.
- `/document:list-types` reports stale or drifted artifacts.
- The user asks to migrate the document schema (e.g. `documentSchemaVersion`
  rose from 1 to 2).
- The user mentions hand-edited skills they'd like reconciled.

## Setup

1. Locate the installed plugin at `${CLAUDE_PLUGIN_ROOT}`. Read
   `.claude-plugin/plugin.json` to confirm it is the `document` plugin.
2. Locate the consuming repository — the cwd, or an explicit `--repo` path
   from the user.
3. Confirm the repo is a git working tree (`git rev-parse --show-toplevel`);
   `/document:upgrade` is destructive enough that uncommitted local
   changes should be visible. If the working tree is dirty, surface that
   to the user before proceeding.

## Operation

### upgrade — refresh the repo against the installed plugin

**Inputs:** optional `--dry-run`, optional `--repo <path>`.

**Steps:**

1. **Scan.** Run the deterministic scanner; capture its JSON:

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/upgrade-scan.py" -C <repo>
   ```

   Output schema (abridged): `{ installed: {…}, artifacts: [ { path, kind,
   provenance, classification, reasons, ... }, ... ] }`. Parse it.

2. **Refuse on `ahead`.** If any artifact's classification is `ahead` —
   its `factory-version`/`generator-version` is **newer** than the
   installed plugin — STOP. Report which artifacts are ahead and tell
   the user: "This repo's artifacts were generated by a newer plugin
   than the one installed. Install the newer plugin, or mark a file
   `provenance: detached` if you intend to keep it ahead." Migration is
   forward-only — never downgrade-regenerate.

3. **Hand-edit detection for `current` Tier-3 artifacts.** For each Tier-3
   artifact classified `current`, regenerate it in memory by running
   `document-define` regenerate against its type definition, compare the
   regenerated body to the existing file body (ignoring `materialized`
   per the regenerate rule). If they differ, **promote to
   `hand-edited`** with the diff retained for the confirmation step.
   This step is the judgment work that justifies a skill rather than a
   pure script — regeneration is a `document-define` operation, not a
   line of code.

4. **Plan.** Present a table to the user. Group by action:

   ```
   ## Upgrade plan

   | Action               | Count | Files                                  |
   |----------------------|-------|----------------------------------------|
   | Install (available)  |   N   | document-events, document-enrich, …    |
   | Regenerate (stale)   |   N   | …                                      |
   | Migrate (config)     |   N   | .config/documents/{root.md,types/…}    |
   | Confirm (hand-edited)|   N   | … (each requires explicit per-file OK) |
   | Orphan (report only) |   N   | … (no action, surface for review)      |
   | No change (current)  |   N   | (omitted unless user asks)             |
   | Detached (skipped)   |   N   | …                                      |
   ```

   `Install (available)` rows are plugin templates the repo doesn't have a
   materialized form of yet — the same op installs them rather than
   requiring a separate `materialize` invocation. A fresh repo's first
   `/document:upgrade` is mostly install rows.

   If `--dry-run`, stop here. Else ask: "Apply this plan? (yes / show diffs / cancel)".

5. **Apply, in this order:**

   0. **Ensure cross-IDE target config exists.** If
      `.config/documents/rulesync.jsonc` does not exist in the consuming
      repo, copy the plugin's default template into place:

      ```bash
      python3 "${CLAUDE_PLUGIN_ROOT}/scripts/materialize.py" \
        -C <repo> --all --no-fanout
      ```

      (`--all --no-fanout` is the idiomatic invocation here — it
      handles `materialize_root_config` plus everything else without
      yet trying to invoke `npx`.) The default config sets
      `targets: cursor, codexcli`. Consumers edit this file to add /
      remove harnesses; future upgrades respect the edit (no
      clobber).
   1. **Install available templates.** For each artifact classified
      `available`, materialize it into the repo by shelling out to:

      ```bash
      python3 "${CLAUDE_PLUGIN_ROOT}/scripts/materialize.py" \
        -C <repo> --template <name>
      ```

      The materializer writes a self-sufficient `.claude/skills/<name>/`
      (with `scripts/` and `evals/`), a repo-local unnamespaced command at
      `.claude/commands/<name>.md` (e.g. `/document-events`), and stages the
      canonical content into `.rulesync/skills/<name>/` for the cross-IDE
      fanout (step 8). After this step the user has the new `/document-<name>`
      commands available with no plugin runtime dependency.
   2. **Config migrations.** For each config file classified
      `migration-needed`, find the migration steps in
      `${CLAUDE_PLUGIN_ROOT}/skills/document-define/references/schema-migrations.md`
      for each version step the file needs (its `schema-version` → the
      installed `documentSchemaVersion`). Run them in order. Each step
      MUST be **idempotent**, **forward-only**, and **partial-failure
      resumable** — re-running a completed step is a no-op, no step ever
      down-migrates, and a crash mid-run leaves the file consistent enough
      that the next `/document:upgrade` picks up where this one stopped.
      Write the migrated file with its `schema-version` bumped.
   3. **Regenerate stale Tier-3.** For each `stale` Tier-3 artifact, call
      `document-define regenerate {type}`. The generator's "preserve
      `materialized` when otherwise unchanged" rule keeps no-op
      regenerations byte-identical.
   4. **Re-materialize stale Tier-2.** For each `stale` `2-materialized`
      skill, re-copy from the plugin's template and update its provenance
      header by running the materializer:

      ```bash
      python3 "${CLAUDE_PLUGIN_ROOT}/scripts/materialize.py" \
        -C <repo> --template <name>
      ```

      A skill and its scripts are **one atomic unit** — the materializer
      re-writes them together. Templates available: `document-events`,
      `document-enrich`, `document-lint`, `document-verify-inferred`.
   5. **Hand-edited confirmation.** For each promoted-to-`hand-edited`
      artifact, use `AskUserQuestion` with three options:
      - **Overwrite** — replace with the regenerated body (the
        intentional edits are lost; surface the diff so the user sees
        what's being discarded).
      - **Detach** — add `provenance: detached` to the artifact's
        frontmatter/header so future upgrades skip it permanently.
      - **Skip** — leave as-is for now; future `/document:upgrade` will
        ask again.
      Show the unified diff before the prompt.
   6. **Orphans** — report, never modify or delete. An orphan means the
      artifact's `type-definition` (or `source`) no longer exists. The
      user decides whether to recreate the source or delete the orphan.
   7. **Install / refresh the pre-commit bundle.** Shell out to:

      ```bash
      python3 "${CLAUDE_PLUGIN_ROOT}/scripts/materialize.py" \
        -C <repo> --githooks
      ```

      This writes `.githooks/document_validator.py` and
      `.githooks/document-validate-staged.py` (self-sufficient, no
      plugin dependency) and either creates a new `.githooks/pre-commit`
      or prepends one invocation line to the existing one (idempotent;
      hand-written checks are preserved). After this step, direct
      shell-edit + `git commit` is also enforced — closing the gap that
      the PreToolUse hook alone leaves open.

      Then verify `core.hooksPath` is set:

      ```bash
      git -C <repo> config --get core.hooksPath
      ```

      If the result is not `.githooks` or empty, ask the user:
      "Pre-commit hook installed but not active — `core.hooksPath`
      isn't pointed at `.githooks/`. Activate now? (Recommended)"
      On yes, run `git -C <repo> config core.hooksPath .githooks`.
      Without this one-time config, the pre-commit script sits on disk
      but git never invokes it.
   8. **Cross-IDE fanout.** All staged content under `.rulesync/skills/`
      and `.rulesync/commands/` now needs to be propagated to each
      configured target. Invoke:

      ```bash
      python3 "${CLAUDE_PLUGIN_ROOT}/scripts/materialize.py" \
        -C <repo> --all
      ```

      The materializer reads `.config/documents/rulesync.jsonc`,
      invokes `npx -y rulesync generate --targets … --features
      skills,commands --simulate-skills --simulate-commands`, and
      surfaces the result in its JSON output under the `fanout`
      key. Three possible statuses:

      - **`ok`** — rulesync produced the per-target output
        (`.cursor/skills/<name>/SKILL.md`, `.codex/skills/<name>/
        SKILL.md`, etc.). Done.
      - **`failed`** — rulesync ran but exited non-zero. Show the
        captured stderr to the user. Decide with them whether to
        retry (after they fix their `rulesync.jsonc`) or proceed
        with the AI fallback.
      - **`deferred`** — `npx` isn't on PATH. **AI fallback:**
        read `${CLAUDE_PLUGIN_ROOT}/skills/document-upgrade/
        references/target-formats.md`. For each target in
        `fanout.targets`, and each skill / command listed in
        `fanout.fallback_plan`:

        1. Read the canonical
           `.rulesync/skills/<name>/SKILL.md` (the staged input).
        2. Apply the target's frontmatter rules from
           `target-formats.md` (strip down to `name + description`
           for skills; the per-target subset for commands).
        3. Write the file at the documented output path
           (`.cursor/skills/<name>/SKILL.md`, etc.).
        4. For non-markdown targets (`.gemini/commands/*.toml`),
           translate accordingly.
        5. Skip target/feature combinations the target doesn't
           support (`windsurf` and `aider` have no command output).

        Report to the user which targets were produced via the AI
        fallback so the provenance is clear. Suggest installing
        Node.js + `npm` to switch to the deterministic path on
        future upgrades.
   9. **Migration of unconfigured target output (first-run only).**
      The scanner's `targets.unconfigured` list contains harnesses
      whose output directories exist on disk but aren't declared in
      `.config/documents/rulesync.jsonc`. Example: a repo that
      previously used the default Copilot output still has
      `.github/skills/<name>/` files, but the new defaults are
      `cursor + codexcli`.

      For each unconfigured target, use `AskUserQuestion`:

      - **Add to config** — append the target name to
        `rulesync.jsonc` so it gets regenerated on future upgrades.
      - **Delete the directory** — remove `<target-dir>/skills/` /
        related output. Use `git rm -r --cached` so the change is
        captured in a single commit.
      - **Skip for now** — leave the directory and re-prompt on
        next upgrade.

      Recommended option label: "Add to config (Recommended) — keeps
      your existing audience covered." Apply the user's choice. The
      one-time prompt is recorded in the resulting `rulesync.jsonc`
      diff so subsequent upgrades are silent (the target is either
      configured or absent).

6. **Re-scan.** After applying, re-run the scanner and report the final
   state: counts by classification, any remaining drift, and any
   `untracked` / `malformed` artifacts noted for human review.

   Note: the re-scan reports the deterministic classes only. `hand-edited`
   detection happens in step 3 (via in-memory regeneration), so a
   hand-edit introduced between the original scan and the re-scan will
   only surface on the next `/document:upgrade` run.

**Output:** a plan summary, then a final report. Counts by classification
before and after, list of files changed, any items deferred.

## Classification glossary

- **`available`** — the plugin ships a template the repo doesn't have a
  materialized form of yet. `/document:upgrade` installs it by shelling
  out to `materialize.py`.
- **`current`** — versions match, type-def-hash matches, body matches a
  fresh regeneration. Nothing to do.
- **`stale`** — older `factory-version`, older `generator-version`, or
  Tier-3 type-def-hash drift. Regenerate.
- **`hand-edited`** — `current` by versions but the generated body has
  diverged from regeneration. Confirm per file.
- **`orphan`** — the artifact's `type-definition` (Tier 3) or `source` no
  longer exists. Report only.
- **`ahead`** — newer than the installed plugin. Refuse the upgrade run.
- **`migration-needed`** (config files only) — `schema-version` below
  installed `documentSchemaVersion`. Migrate per
  `schema-migrations.md`.
- **`detached`** — artifact carries `provenance: detached`. Skip
  permanently.
- **`untracked`** / **`malformed`** — report, never act.

## Output discipline

- Always lead with a direct answer: "Plan would change N files…" or
  "Nothing to do — N artifacts, all current."
- Never silently overwrite a hand-edited file. Per-file `AskUserQuestion`
  is non-negotiable here.
- Never act on `--dry-run`.
- Never downgrade-regenerate an `ahead` artifact.
